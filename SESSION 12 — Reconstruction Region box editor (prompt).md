## Step 1 — get a real `.rsbox` out of RealityScan before writing one

### The trap: the frame. It will not error, it will keep the sky and delete the scene

Three rotations are already in play and only one of them belongs in the file:

| Where | What |
|---|---|
| `rc_postprocess.align_pointcloud_to_cameras` | rotates `pointcloud.ply` by `Rx+90`, `(x,y,z) -> (x,-z,y)`, and stamps `_ROTATED_MARKER` — `comment 3dgs-pipeline-app: rotated Rx+90 (RC Z-up -> NeRF Y-up)` — into the header |
| `viewer/frame.ts` | draws RS-frame content with a **display** `Rx+180` |
| the "Flip up" toggle | another **display** `Rx+180`, at the user's whim |

`-exportReconstructionRegion` writes the region in RS's **native Z-up** frame —
the frame `pointcloud.ply` was in *before* `rc_postprocess` touched it. So:

* the canonical app frame is the NeRF one (what is on disk after normalisation):
  `nerf = Rx+90 · rc_native`, inverse `(x, y, z) -> (x, z, -y)`;
* both display rotations are display only and must be stripped before anything
  is written to disk;
* whether the preview is in the NeRF frame at all depends on
  `rc.normalise_for_lfs`. **Read the marker, never assume it** — a project
  aligned with normalisation off has a preview already in RS's native frame.

Prove the frame rather than reasoning about it: after parsing
`region_auto.rsbox`, compute `coverage()` of the sparse cloud in each candidate
frame and log it. RS's automatic region contains most of the cloud by
construction, so the correct frame scores ~0.9 and the wrong ones score ~0. Keep
that number in the log line of every run — it is the one cheap check that the
whole chain is still aligned:

```
[RS] Region: 214 883/286 104 sparse points inside (75.1 %), from region_auto.rsbox.
```

## Step 4 — the editor in the viewer

`frontend/src/components/viewer/` — `PointCloudCanvas.tsx` already owns the
`THREE.Scene`, the `OrbitControls` and the camera rig; `SceneViewer.tsx` owns
the toolbar.

* **No new dependency.** `three/examples/jsm/controls/TransformControls.js`
  ships with the `three@0.169` already in `package.json`. Adding a package would
  need a §10 licence row; adding this one needs nothing, so use it.
* New `viewer/regionBox.ts`: the box as a `THREE.Mesh` (unit `BoxGeometry`,
  scaled) with a transparent material and a `LineSegments` edge overlay, parented
  to a group that gets the same `applyUpFix` treatment as the cloud — the box
  lives in the scene, inherits the display flips, and must be read back through
  their inverse.
* `TransformControls` in three modes (translate / rotate / scale) toggled from a
  small toolbar, with `addEventListener('dragging-changed', …)` disabling
  `OrbitControls` while a gizmo is dragged. Miss that and every drag also orbits
  the camera.
* A numeric readout **and numeric entry** for centre / size / rotation beside the
  viewer. A gizmo alone cannot place a box repeatably, and a box 2 cm out in Z is
  invisible on screen and fatal to the mesh prompt B builds from it.
* Buttons: **Fit to cloud** (`region_from_pointcloud`), **Reset to RS's region**
  (re-read `region_auto.rsbox`), **Save region** (the `PUT`), and a live
  "n/N sparse points inside (x %)" computed in the browser from the loaded
  preview so it updates while dragging.
* Opt-in: `SceneViewer` gains a `withRegion` prop, passed only from
  `Step3_RC.tsx`, and only when `rc.region.mode !== "off"` and the preview is a
  point cloud. Steps 4 and 5 must not grow a box editor.
